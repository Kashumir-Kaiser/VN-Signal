# Audited recovery lineage — migration 077

The two ABR exceptions illustrate a false negative in migration 076: offline replay deliberately preserves immutable `equity_ohlcv_quarantine` bytes and route, while accepted rows can be projected after validation. Exact OHLCV/byte checks alone do not justify accepting arbitrary quarantined responses. The ABR dates trace to landing 11 and the recorded recovery of its owning ingest job. Version 076 did not consider that acceptance path.

Migration 077 introduces `vci-exact-row-v2`, preserving v1 observations. For quarantine candidates it requires exactly one owning job, matching source/ticker/requested route, bounded original dates, matching accepted current job and latest audit result, a reviewed validator version, provider source/route attribution, byte and stored-body verification, exact dated row equality, and absence of a row-date quality issue. Unknown newer validators block older approval. Source evidence snapshots retain the quarantine route, owning job, audit and quality findings in the input fingerprint; no raw or core data is rewritten. The two approved validator versions are the existing auction-extrema v1 and its empty-response v2 successor; approval is explicit, not an arbitrary version prefix match.

Review found the recovery lookup lacked an index on ingest_jobs.landed_id and was evaluated twice. The migration adds the partial lookup index and computes evidence once in the materialized landing stage. Symbol-scope bounds remain 1–100, operational batches use 15 symbols.

Baseline and recovery regression assertions passed on the disposable database (`phase2_vci_lineage_077_review_20261024.log`). Cases cover missing ownership/audit, valid recovery, timezone/retry stability, later quality changes, unknown newer validator, conflicting ticker, original date bounds and ambiguous ownership. The first recovery fixture evaluated a mutating function and a dependent read inside one Boolean expression; splitting them into sequential statements corrected its evaluation-order assumption. The original failure and diagnostic retry remain in the evidence directory. Required Go tests/vet and all 32 Python tests passed (`*_077_20261024.log`).

The fresh full two-pass harness and report-clone migration are pending, not claimed as passes. A hidden serial follow-up process (PID/start identity in `phase2_serial_followup_077_20261024.status.json`) waits for successful completion of the identified feature build. It fingerprints migration/test inputs, refuses changed inputs or a failed/missing feature process, then runs the fresh harness, applies 077 only on success, and archives full lineage in independently committed bounded batches. It performs no live market calls and records terminal status/errors. The queue was verified alive in `waiting_for_features`; 077 is not yet applied to the report clone.
