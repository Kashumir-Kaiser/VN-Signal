# Phase 2 data-contract audit for Phase 3

**Reviewed:** migrations 034–077 and catalog metadata from `vnsignal_phase2_076_review_20261024_disposable` after migration 077. This is a schema/documentation audit only; no market rows were queried or exported. Column metadata is in [phase2_schema_columns_077_20261024.csv](phase2_schema_columns_077_20261024.csv), and constraint definitions are in [phase2_schema_constraints_077_20261024.csv](phase2_schema_constraints_077_20261024.csv).

## Current inventory

The catalog export contains 978 columns across 77 relations: 1 in `raw`, 28 in `core`, 11 in `feat`, 37 in `ops`; `ml` has no tables or views. This confirms that model-run, fold, model, prediction, recommendation and backtest contracts are still future work. The existing [DATA_CONTRACT.md](../../DATA_CONTRACT.md) is materially stale: it describes `feat` and `ml` as future schemas and does not document the Phase 2 relations or the VCI lineage archive.

Current contracts center on:

- `raw.landings`: immutable payload and exact-byte checksum, including route-specific VCI recovery evidence. `core` contains provider-keyed daily bars, source observations, fundamentals, calendar/session, security/lifecycle, price-limit, and adjustment evidence.
- `feat`: `features_daily`, `labels_daily`, the Phase 2 V3 label targets, liquidity tiers, market context, and training eligibility/gap views.
- `ops`: ingestion and quota audit, quality and reprocessing audit, chunk/build accounting, scope/eligibility, and VCI lineage observations/batches. `ops.phase2_vci_bar_lineage` v2 snapshots a route and, for approved quarantine recovery, an audit/quality-evidence object. This records source-projection acceptance; it does not establish listing tenure or independent historical publication.

## Semantic gaps to close before Phase 3

1. **Feature matrix contract.** Publish the ordered model-input allowlist by feature version/hash, with each field's type, units, null meaning, source/basis, and availability time. Distinguish `traded_value` from the derived turnover proxy; distinguish price units/basis and adjustment vintage; define cross-sectional ranking population and treatment of excluded/ineligible names. State explicitly that `built_at` is not feature availability and that no post-signal value may enter a row.
2. **Training-row join and eligibility.** Specify the unique key and exact join between current-hash `feat.features_daily`, `feat.labels_daily`, and `feat.phase2_training_eligible_v3`. Use only `READY` labels of the approved label version and current feature hash, honor `phase2_training_gaps_v3` cooldown and membership/label gates, and document which horizons are trained. The eligibility view exposes the excess-return outcome but is not a complete model matrix.
3. **Target timing and use.** Define signal close, next-session entry, horizon exit, effective-session calendar, missing-session/episode behavior, adjustment-vintage consistency, winsorization scope, volatility scaling, and execution-weight meaning. Labels are future outcomes and must never be predictors; `execution_weight` is a target/sample-weight input only under its documented exact evidence rules.
4. **Point-in-time limits.** For every feature/source family, document the timestamp that makes the value knowable at signal time. Fundamental features must join on `available_at`, not `period_end`; archived/restated OHLCV and source `fetched_at` do not by themselves prove historical publication. VCI lineage's retrieval timestamp and audited recovery acceptance are provenance, not a point-in-time availability guarantee.
5. **Identity and survivorship.** Treat `symbol_id`/ticker observations as code-level identity, not proof of one continuous legal issuer. `listing_snapshots`, lifecycle evidence, and current membership do not imply IPO/delisting dates or historical investability. Define how ambiguous, absent, or conflicting historical membership is excluded and surfaced.
6. **Validation protocol.** Record the exact expanding-window split algorithm, effective-session index, 20-session embargo/purge for overlapping labels, minimum training history, test-block boundaries, and deterministic seeds. Define per-fold metrics and promotion thresholds before training; report all trials and do not promote a champion if the required evidence is absent.
7. **Reproducibility and artifact schema.** Before writing model outputs, define `ml` tables and immutable keys for run, dataset snapshot, feature hash, label version/horizon, fold, seed, parameters, metrics, model bytes/hash, predictions, calibration, promotion decision and backtest. Hash all inputs, configuration and code revision; define idempotent rerun/conflict behavior. The current database has no `ml` relations, so no model or prediction contract should be inferred from the SQL feature tables.
8. **Downstream safety boundary.** Specify that proxy turnover is for research ranking only, not executable capacity, and that suggestions remain disabled without a valid promoted champion and the required tradability/price-limit/lot-size/settlement evidence.

Phase 3 should begin only after these semantics and acceptance tests are explicit. In particular, add leave-future-out checks for every input family, feature parity against the SQL reference, and purged-walk-forward fixtures that prove no training label overlaps a test interval.
